# VlogCraft Studio 3.5.6 HDR10+ authoring

The development branch starts at PR #12 head `60e233b72319607936a1afd48e7f6572f7d364da`. Retain the verified complete-source preservation path, existing HDR10/SDR rendering and project compatibility. Qualify generated sources before bounded, read-only private-camera checks. Publish evidence in separate feasibility, metadata, export and delivery checkpoints.

## Feasibility policy

Reuse the 3.5.5 encoded/decoded audit. The 7,619 readable camera blocks have a nonzero value in the reserved 5% entry for the paired 5%/10% positions. Retain the version-1 preservation rejection. Keep malformed, unsupported and implementation-limited cases distinct from readable nonconforming blocks. Playback compatibility requires a separate device test. The source files and cached indexes remain unchanged. [SMPTE ST 2094-40:2020, §8.5.4](https://pub.smpte.org/pub/st2094-40/st2094-40-2020.pdf).

Complete-source stream copying preserves the original creative metadata only when the existing identity and conformity checks pass. A rendered master needs fresh statistics across all final pictures, including unchanged areas in an edited timeline. A hybrid path would additionally need a proven picture-identity and creative-intent policy at each boundary, so it stays outside this checkpoint.

## Proposed authoring and verification

Analyze the independently decoded final Main10/PQ Rec.2020 encode. Use one whole-frame processing window and a one-frame analysis interval. Generate maximum linear RGB by component, average maxRGB and exact nearest-rank percentiles at the defined positions, including the version-1 99.98% substitution and reserved values. A per-frame histogram and bounded decoding avoid a raw video intermediate. Optional creative Bézier tone mapping and unmeasured mastering information are outside the algorithm. Retain only explicit mastering declarations supplied for the managed output. [SMPTE ST 2094-40:2020, §§4, 8–10](https://pub.smpte.org/pub/st2094-40/st2094-40-2020.pdf).

Transport is a separate stage. Test metadata insertion after the existing CPU libx265 encode to preserve the same pictures, HEVC compression, audio and rational timestamps. Use FFprobe decoded frame side data and independently computed picture statistics before making Edited Master selectable. Require timestamp and picture/audio preservation across insertion, verify HEVC signaling and keep failure atomic. Additional decode and compressed I/O will cost export time. Record that cost on matched output and keep the SDR/static paths unchanged.

x265 accepts supplied dynamic metadata when built with the applicable support. `hdr10plus_tool` extracts or inserts existing metadata. Neither tool generates the final-picture statistics on its own. The published AMF HEVC interface documents HDR static metadata. Arbitrary ST 2094-40 authoring via this build of AMF remains unverified. The existing FFmpeg/x265 build and NumPy provide the intended implementation dependencies. No installer distribution or certification is implied by local testing. [x265 documentation](https://x265.readthedocs.io/en/latest/cli.html), [hdr10plus_tool upstream](https://github.com/quietvoid/hdr10plus_tool), [AMF HEVC API](https://github.com/GPUOpen-LibrariesAndSDKs/AMF/blob/master/amf/doc/AMF_Video_Encode_HEVC_API.md), [dependency and distribution notes](../THIRD_PARTY.md).

The current generator implements descriptive Profile A data. Section 8.6 permits zero as the explicit uncalculated FractionBrightPixels value. The target is zero and no creative curve is emitted. The consortium's content profile requires mastering-display color-volume metadata, so an Edited Master must use the operator's known mastering-display parameters. The existing 3.5.5 preservation policy remains separate. Two deterministic statistics tests passed for flat black and mid-gray, distinct RGB maxima, a split distribution and moving highlights, exact reserved/rank rules and escaped SEI roundtrip. [HDR10+ white paper](https://hdr10plus.org/wp-content/uploads/2023/11/HDR10_WhitePaper.pdf).

## Edited Master checkpoint

Render with the existing high-precision managed PQ compositor and CPU HEVC encoder. Decode the resulting 10-bit file in presentation order, reconstruct full-range PQ GBR16 with explicit Rec.2020 nonconstant-luminance and bilinear chroma reconstruction, and linearize by the ST 2084 EOTF. Accumulate a histogram of per-pixel maxRGB in row tiles and index short fixed-length metadata records by output frame number. There is no uncompressed intermediate. Fragment the original compressed video into one sample per MP4 fragment. Match every fragment payload to the original packet, insert the registered prefix SEI before that picture's first VCL NAL, and remux with original AAC. Look up the authored record using the original rational PTS, including B-picture reordering.

Before publishing, check stream configuration, original versus output PTS, DTS, durations, audio hashes and exact compressed picture bytes plus the expected SEI. Any failure stops publication. The same derived settings are scoped to the requested export and leave the saved project format and undo data intact. The Render timeline and original preservation paths retain their behavior. Actual titles, stills, color grades, spatial clip transforms, artistic curves, masks, keyed overlays, HLG and Log remain gated in managed HDR. Qualified video layers can be composited with linear exposure, fades and opacity animation.

A 29.97 fps test with audible audio and short segments exposed a managed HDR mux timing defect. Each independently encoded GOP had a different reorder delay. The MP4 muxer advanced a colliding decode timestamp to one tick after its predecessor, producing a one-tick picture duration. Managed PQ now verifies the concatenated presentation timestamps and applies a continuous decode clock with the minimum global decode delay that preserves decode order and all PTS. Picture packets remain compressed and byte-identical. The same fixture passed with all exact durations, as did a VFR trim at 2× with held frames and the expected 100/500/1,000 cd/m² source intervals.

The source Windows GUI passed 12 edited frames with exact decoded SDR/PQ composite video and audio against the static HDR10 export. Independent FFprobe decoded metadata and a scalar ST 2084 oracle agreed with the final decoded pictures. The initial test fixture created duplicate track IDs; the second run found a missing tracks argument in export-only validation. Both failures were retained and the normal Export path passed after correction. The initial independent mixed-layer test also exposed FFprobe JSON's repeated field names. The XML oracle preserves all channel maxima and percentile records.

The Samsung profile uses the verified CPU authoring path with a 4K60 canvas and CRF 17. The separate YouTube profile uses HDR10/PQ HEVC Main10 at 4K60, a 75 Mb/s video target and 48 kHz stereo AAC with a 384 kb/s target. That is an export target; a short compressible clip will come in below it. YouTube's HDR requirements allow HEVC at this cadence. No upload or transcode test was run. Playback on the owner's Samsung TV remains pending.
